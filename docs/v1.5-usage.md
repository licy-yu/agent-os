# SwarmOS V1.5 使用与运维手册

本文面向本地开发、局域网虚拟机试用和生产候选部署。命令按当前 REST 合同编写；所有示例中的 `<...>` 都必须替换。尚未完成的能力会明确标注，不以“表已创建”代替“功能已可用”。

## 1. 先选运行模式

| 模式 | 需要的进程/依赖 | 适用场景 | 当前边界 |
| --- | --- | --- | --- |
| `LEGACY` | PostgreSQL、Redis、NATS、control-plane、worker | 本地开发、兼容旧 V1、最短验证路径 | 没有 Temporal Workflow History；Task 执行主链可用 |
| `TEMPORAL` | LEGACY 全部组件 + Temporal Server + workflow-worker | 需要耐久 Run Signal 与协调历史 | Temporal 只协调 Run；Scheduler、Agent Task 和模型执行仍走 control-plane/NATS/worker |

默认 `configs/config.yaml` 设置 `SWARMOS_TEMPORAL_ENABLED=false`。未填写 `executionEngine` 时，服务会在 Temporal Gateway 就绪时选 `TEMPORAL`，否则选 `LEGACY`；显式请求 `TEMPORAL` 但服务未启用会返回 503 `TEMPORAL_DISABLED`。

控制台的新建表单当前默认选 Temporal。使用默认本地配置时，务必在表单里改选“数据库兼容模式（LEGACY）”。

## 2. 本地 LEGACY 启动

### 2.1 前置条件

- Go 1.24；
- Node.js 与 npm；
- Docker Engine / Docker Desktop，支持 Compose v2；
- 可选 `jq`，用于从 API 响应提取 ID；
- 真实模型执行才需要 `OPENAI_API_KEY`，确定性验收可使用 `mock/deterministic`。

### 2.2 构建控制台并启动基础设施

```bash
cd /path/to/agent-os/web
npm ci
npm run build
cd ..

docker compose up -d --wait postgres redis nats
docker compose ps
```

本地 compose 只启动 PostgreSQL、Redis 和 NATS，不会启动 SwarmOS 进程，也不会启动 Temporal。

### 2.3 启动两个应用进程

终端 A：

```bash
go run ./cmd/control-plane -config ./configs/config.yaml
```

终端 B：

```bash
go run ./cmd/worker -config ./configs/config.yaml
```

控制面和 worker 启动时会运行内嵌 PostgreSQL 迁移。检查：

```bash
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/readyz
curl -fsS http://127.0.0.1:8080/
```

`/healthz` 主要兼容进程/数据库健康检查；`/readyz` 还会检查 PostgreSQL、Redis、NATS，以及启用时的 Temporal 连接。两者都不证明普通 worker 或 workflow-worker 正在消费。

浏览器打开 `http://127.0.0.1:8080/`。

`.env` 不会被 `go run` 自动加载；它只会被 production compose 的 `env_file` 或 systemd 的 `EnvironmentFile` 读取。本地若要覆盖配置，应在启动两个进程的同一 Shell 会话显式设置环境变量，例如：

```bash
export SWARMOS_API_KEY='local-only-example-key'
export OPENAI_API_KEY='<真实值，仅在需要真实模型时设置>'
```

PowerShell 对应写法：

```powershell
$env:SWARMOS_API_KEY = 'local-only-example-key'
$env:OPENAI_API_KEY = '<真实值，仅在需要真实模型时设置>'
```

## 3. API Key

### 3.1 服务端设置

`SWARMOS_API_KEY` 只能从环境变量注入，不从 YAML 读取。开发环境允许空值；Key 为空时 `/api/*` 不校验密钥，但仍注入服务端配置的固定 tenant 与 subject。

生产必须显式设置环境和强 Key：

```bash
export SWARMOS_ENVIRONMENT=production
export SWARMOS_API_KEY="$(openssl rand -hex 32)"
```

`production` 模式下 Key 少于 32 字符会导致进程拒绝启动。不要把 Key 放在 URL、Git、截图、日志或 Interaction 的普通 `resolution` 中。

### 3.2 curl 调用

两种 Header 均支持，推荐 Bearer：

```bash
BASE_URL='http://127.0.0.1:8080'
API_KEY='<与服务端完全一致>'

curl -fsS \
  -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs?limit=100"
```

也可以使用：

```bash
curl -fsS -H "X-API-Key: ${API_KEY}" "${BASE_URL}/api/v1/runs"
```

### 3.3 控制台录入

打开控制台后，点击右上角 `API KEY`，录入服务器中的同一值。前端将 Key 作为 Bearer Header 发送，并只保存到当前标签页的 `sessionStorage`；关闭标签页后清除，不写 URL、Cookie 或长期 localStorage。

静态页面、`/healthz` 和 `/metrics` 本身不受 API Key 保护，所以“页面能打开但所有面板 401”通常就是浏览器尚未录入正确 Key。

## 4. 第一次完整 Run

### 4.1 先注册 AgentTemplate

Planner 的 Catalog 只信任已启用 AgentTemplate 与 Tool Registry。没有任何 capability 时，创建 Run 会返回“当前没有启用的 Agent 能力”。先注册一个确定性模板：

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/agent-templates" \
  -d '{
    "name":"local-general",
    "role":"executor",
    "prompt":"严格执行任务并提交可验证证据",
    "model":"mock/deterministic",
    "skills":{"general":1},
    "tools":["echo"],
    "permissions":[],
    "templateVersion":"1.0.0",
    "contextWindow":"32000",
    "riskZone":"sandbox",
    "costPer1KTokensMicros":"0"
  }'
```

保存响应中的 `id` 为 `<TEMPLATE_ID>`。该模型不需要 OpenAI Key，但仍经过真实 PostgreSQL、NATS、Scheduler、Worker、Tool Gateway、Checkpoint 和 Verification 路径。

### 4.2 创建 LEGACY Run

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/runs" \
  -d '{
    "name":"本地验收 Run",
    "goal":"生成一份可验证的确定性结果",
    "budgetTokens":300000,
    "budgetCostMicros":5000000,
    "maxAgents":1,
    "priority":50,
    "executionEngine":"LEGACY"
  }'
```

保存响应 `id` 为 `<RUN_ID>`。不传 `plan` 时，当前服务只会根据 Catalog 的第一个 capability 生成单 Task 计划；它不是通用的多任务 LLM Planner。

### 4.3 为 Run 注册 Agent

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/agents" \
  -d '{
    "templateId":"<TEMPLATE_ID>",
    "swarmId":"<RUN_ID>",
    "name":"local-agent-1"
  }'
```

Run 在创建事务中已经进入 `RUNNING`，Task 会先处于 READY/BLOCKED。Agent 注册后 Scheduler 才有可绑定实例。

### 4.4 观察执行

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/tasks"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/timeline?limit=100"
```

控制台每 5 秒刷新 Run/Attempt，也可以手动点刷新。Run 完成需要 Reviewer/Verification 接受持久化证据，不以模型输出的文本为准。

## 5. Run 操作

### 5.1 查询列表与详情

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs?limit=100"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>"
```

Run 返回预算/实耗、Task 状态聚合、当前 PlanVersion、待处理 Interaction 数和 Temporal Workflow ID。列表统一返回 `{"items": [...]}`。

### 5.2 Pause、Resume、Cancel

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/runs/<RUN_ID>:pause" \
  -d '{"reason":"人工检查"}'

curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/runs/<RUN_ID>:resume" \
  -d '{"reason":"检查完成"}'

curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/runs/<RUN_ID>:cancel" \
  -d '{"reason":"用户取消"}'
```

Pause 只阻止后续调度并等待安全边界，不会假装撤销正在外部系统发生的副作用。Cancel 是终止动作；已经发生或状态未知的 Effect 仍需对账。

这些 Run 动作在数据库端使用版本 CAS，但当前 HTTP 合同不接收客户端 `expectedVersion`，后端也不消费 Run 动作的 `Idempotency-Key`。超时后先 GET 刷新状态，再决定是否重试。

### 5.3 Replan

Replan 必须有非空 `reason`，并且 Run 已 Pause，或处于 WAITING_USER、VERIFYING、DEGRADED。推荐顺序：

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/runs/<RUN_ID>:pause" \
  -d '{"reason":"准备修改目标"}'

curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  "${BASE_URL}/api/v1/runs/<RUN_ID>:replan" \
  -d '{
    "reason":"验收条件发生变化",
    "goal":"生成结果并补充机器可读摘要"
  }'
```

成功后创建 Plan V2，旧 Plan 变为 SUPERSEDED，未终态 Task 被取消，已成功 Task、Artifact、Effect 和 GateResult 保留。若仍有 `EXECUTING / UNKNOWN / RECONCILING / COMPENSATING` Effect，Replan 返回 409，必须先对账或补偿。

当前 Run 详情给出 `currentPlanVersionId`；读取具体计划：

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/plans/<PLAN_VERSION_ID>"
```

## 6. Approval 与 Input Inbox

### 6.1 列出待处理项

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/interactions?status=WAITING&runId=<RUN_ID>&limit=100"
```

`status=PENDING` 是前端兼容别名，服务端会转成真实状态 `WAITING`。处理前保存响应中的 `id`、`interactionType`、`allowedActions` 和当前 `version`。

### 6.2 Approval

批准：

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: approve-<稳定唯一值>' \
  "${BASE_URL}/api/v1/interactions/<INTERACTION_ID>:approve" \
  -d '{"version":1,"resolution":{"comment":"已核对变更范围"}}'
```

拒绝：

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: reject-<稳定唯一值>' \
  "${BASE_URL}/api/v1/interactions/<INTERACTION_ID>:reject" \
  -d '{"version":1,"resolution":{"reason":"超出变更窗口"}}'
```

R3 Effect 的审批与授权/封存会在同一数据库事务中提交。Worker 会把 Attempt 持久化为 `WAITING` 并确认消息，批准后重新投递同一个 Attempt、递增 fencing token，不消耗 JetStream 的长等待投递次数；拒绝或超过 `expiresAt` 会原子终结 Effect、ToolCall、Attempt、Task、Agent 与 Run。网络超时重试同一个用户动作时，必须复用相同 `Idempotency-Key` 和相同请求体；同键异参返回 409。

### 6.3 Input / Choice / Edit / Auth

普通 Input 使用 resolve：

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${API_KEY}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: resolve-<稳定唯一值>' \
  "${BASE_URL}/api/v1/interactions/<INTERACTION_ID>:resolve" \
  -d '{
    "action":"resolve",
    "version":1,
    "resolution":{"value":"用户补充的结构化输入"}
  }'
```

AUTH 类型只能提交：

```json
{
  "action": "resolve",
  "version": 1,
  "resolution": {"credentialRef": "vault://project/service-key"}
}
```

不能提交明文密码或 Token。若收到 409 version conflict，重新 GET Interaction 获取最新版本，不要盲目增加 version。

当前 R3 Approval 已与 Worker 的持久等待、原 Attempt 恢复、超时收口接线；通用 Input 尚不能保证自动把 Run 切到 WAITING_USER、向 Temporal 发送恢复 Signal并从原 Checkpoint 继续。该端到端场景仍列为待生产/集成验收。

## 7. Artifact、Timeline、Scheduler Explain 与完成证据

### 7.1 Artifact

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/artifacts?limit=100"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/artifacts/<ARTIFACT_ID>"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/artifacts/<ARTIFACT_ID>/lineage?direction=both&depth=5"
```

Artifact API 返回描述符、版本、哈希、URI/ObjectKey、验证状态和血缘。当前没有通用对象上传/下载端点；URI 指向的外部对象是否可取决于部署方是否提供对应对象存储。

### 7.2 Timeline

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/timeline?limit=200"
```

Timeline 聚合 Run/Task/Attempt/Effect/Interaction 等事件，包含 actor、correlation/causation、traceId 和 payload。它是运维证据，不是消息队列消费进度接口。

### 7.3 Scheduler Explain

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/scheduler-decisions?limit=100"
```

结果包含候选、Filter 拒绝原因、Queue Score、被选 Agent 和选择理由。如果 Run 一直 READY，应先查看这里是否是 capability、tool/model、风险域、预算、Agent 状态或并发槽不匹配。

### 7.4 Verification 与 Completion Manifest

```bash
curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/runs/<RUN_ID>/verifications?limit=100"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/verifications/<VERIFICATION_ID>"

curl -fsS -H "Authorization: Bearer ${API_KEY}" \
  "${BASE_URL}/api/v1/completion-manifests/<MANIFEST_ID>"
```

完成事件 `run.completed` 的 Timeline payload 包含 `completion_manifest_id` 和 `final_artifact_id`。当前没有“按 Run 列出 Completion Manifest”的快捷端点，应从该事件取 Manifest ID 后查询。设计要求的 Cost Summary 当前主要体现在 Run 预算/实耗字段，独立成本账本尚未完全闭环。

## 8. 启动 TEMPORAL 模式

### 8.1 本地 Temporal CLI 路径

仓库不安装 Temporal CLI。已经安装 CLI 时，可在独立终端启动开发 Server：

```bash
temporal server start-dev --ip 127.0.0.1 --port 7233
```

然后为 control-plane 与 workflow-worker 设置相同配置：

```bash
export SWARMOS_TEMPORAL_ENABLED=true
export SWARMOS_TEMPORAL_ADDRESS=127.0.0.1:7233
export SWARMOS_TEMPORAL_NAMESPACE=default
export SWARMOS_TEMPORAL_TASK_QUEUE=swarmos-runs-v1-5
```

依次启动三个 SwarmOS 进程：

```bash
go run ./cmd/control-plane -config ./configs/config.yaml
```

```bash
go run ./cmd/worker -config ./configs/config.yaml
```

```bash
go run ./cmd/workflow-worker -config ./configs/config.yaml
```

创建 Run 时使用 `"executionEngine":"TEMPORAL"`，或在 Temporal Gateway 就绪时省略该字段。Run 返回的 `temporalWorkflowId` 与 `temporalRunId` 非空才说明 Workflow 身份已投影到 PostgreSQL。

### 8.2 Linux VM 的 production compose 候选路径

`compose.production.yaml` 使用 Linux host network 连接宿主机 PostgreSQL/Redis/NATS，并为 Temporal 使用独立 PostgreSQL。它不适合作为未经修改的 Windows Docker Desktop 部署方案。

先准备三份 Linux 二进制和控制台：

```bash
CGO_ENABLED=0 make build
```

准备 `.env`，至少覆盖：

```dotenv
SWARMOS_ENVIRONMENT=production
SWARMOS_DATABASE_DSN=postgres://<user>:<password>@127.0.0.1:<port>/<db>?sslmode=require
SWARMOS_REDIS_ADDR=127.0.0.1:<port>
SWARMOS_REDIS_PASSWORD=<redis-password>
SWARMOS_NATS_URL=nats://127.0.0.1:<port>
SWARMOS_API_KEY=<至少32字符随机值>
SWARMOS_TEMPORAL_DB_PASSWORD=<与业务库不同的随机值>
SWARMOS_TENANT_ID=<租户UUID>
SWARMOS_API_SUBJECT=production-operator
```

如果目标机已经有可用的业务 PostgreSQL、Redis 和 NATS 配置，可以用仓库脚本补齐其余生产变量。请使用拥有 `.env` 的部署账户执行（当前目标机是 `hale`，不要改用 `sudo`）；脚本不会 `source` 或打印 `.env`，仅在 API Key/Temporal 密码缺失或不足 32 字符时使用系统 CSPRNG 生成新值，并以 `0600` 权限原子替换文件：

```bash
python3 scripts/configure-production-env.py --path /srv/projects/agent-os/.env
```

脚本只输出配置是否就绪以及“本次生成了哪些密钥名”，不会输出密钥值；可重复执行，已有合格密钥会保持不变。执行后必须先用 `docker compose -f compose.production.yaml config --quiet` 验证变量插值，再启动服务。

当前工作树已放行三个二进制进入镜像，compose 强制 `production` 并包含 workflow-worker，smoke 会携带 API Key且允许空库，`/readyz` 会检查关键连接。仍应先在发布 commit 上核对这些文件，再执行：

```bash
docker compose -f compose.production.yaml config
docker compose -f compose.production.yaml up -d --build
docker compose -f compose.production.yaml ps
```

如果宿主机没有既有 PostgreSQL/Redis/NATS，可以先用本地 compose 作为单机候选基础设施；正式生产仍应独立规划备份、HA、TLS 和访问控制。

systemd 已包含 `swarmos-workflow-worker.service`。安装脚本始终安装三个 unit，但只在 `.env` 的 `SWARMOS_TEMPORAL_ENABLED=true` 时启用并启动 workflow-worker；LEGACY 模式会明确停用它。现有 unit 固定 `User=hale`、`Group=hale` 和 `/srv/projects/agent-os`；目标机不同就必须在安装前审查并修改 unit，`SWARMOS_PROJECT_DIR` 本身不会改写 unit 内的绝对路径。

## 9. 使用虚拟机 IP 访问

默认 HTTP 地址是 `0.0.0.0:8080`，因此只要虚拟机网络和防火墙允许，就可以从宿主机访问：

```text
http://<VM-IP>:8080/
```

在 Linux VM 查询地址：

```bash
hostname -I
ss -lntp | grep ':8080'
```

建议只对宿主机或管理网段开放 8080。例如使用 UFW 时，应把 `<管理网段>` 换成实际网段：

```bash
sudo ufw allow from <管理网段> to any port 8080 proto tcp
```

如果 VM 使用 NAT，需要配置端口转发；Host-only/桥接网络则使用该网卡的 VM IP。云 VM 还要同时检查安全组。

安全边界：

- 当前仓库没有 TLS 反向代理，API Key 在纯 HTTP 上会明文经过网络；只在可信隔离网试用。
- 公网使用必须放在 HTTPS、VPN 或 SSH 隧道后。
- 不要开放 9090 gRPC；它当前没有与 HTTP 等价的 API Key/TLS 中间件。
- 7233、9465、数据库、Redis、NATS 端口应留在回环或可信内网。

SSH 隧道是一条更安全的临时路径：

```bash
ssh -L 8080:127.0.0.1:8080 <user>@<VM-IP>
# 然后本机打开 http://127.0.0.1:8080/
```

## 10. 故障排查

| 症状 | 最可能原因 | 处理 |
| --- | --- | --- |
| 控制台页面能开，所有面板 401 | SPA 不鉴权，但 `/api/*` 需要 Key | 点击右上角 API KEY；核对服务端 `SWARMOS_API_KEY`，不要在 URL 传 Key |
| 创建 Run 返回“没有启用的 Agent 能力” | Catalog 没有 enabled AgentTemplate capability | 先按 4.1 注册模板；确认 tenant 一致 |
| 默认本地创建返回 503 `TEMPORAL_DISABLED` | 控制台默认选 Temporal，服务默认关闭 | 改选 LEGACY，或完整启动 Temporal + workflow-worker |
| Run 一直 READY/RUNNING，没有 Attempt | 没注册 Run Agent、模板不匹配、NATS/worker 不在线 | 查 `/scheduler-decisions`、Agent 列表、worker/NATS 日志与指标 |
| `/healthz` 是 ok 但 Task 不执行 | healthz 主要检查数据库；即使 readyz 成功也不证明 Worker 在消费 | 查 `/readyz`，再检查普通 worker、workflow-worker、NATS/Temporal backlog、日志与指标 |
| TEMPORAL Run 有 Workflow ID 但不动 | Temporal Server 可连，但 workflow-worker 无消费者或 TaskQueue 不一致 | 核对三个 Temporal 环境变量与 workflow-worker 日志 |
| Pause/Replan 返回“Signal 待对账” | PostgreSQL 已提交，Temporal Signal 暂时失败 | 先 GET Run；动作可能已生效，等待投影轮询，不要立即重复制造相反操作 |
| Replan 返回 409 | Run 未到安全点、版本竞争或存在未决 Effect | 先 Pause/刷新；列出 Effects，完成 Reconcile/Compensate 后再试 |
| Interaction 返回 400 | 缺 `Idempotency-Key`、version 非正数、resolution 不是对象 | 用读到的当前 version 和稳定 Key；按文档 JSON 发送 |
| Interaction 返回 409 | version 已变化或同幂等键提交了不同请求 | 重新 GET；相同动作重试复用同 Key/同 body，新动作使用新 Key |
| Effect 为 UNKNOWN | 外部系统结果不确定 | 禁止直接 Retry；查询稳定 `externalRef` 后调用 reconcile；终态必须提交结构化 `evidence`，`result + evidence` 不得超过 64 KiB |
| Artifact 有 URI 但无法下载 | 当前只保证描述符/血缘，没有通用对象存储 API | 检查部署方对象存储适配；不要把 URI 非空等同于对象存在 |
| Run COMPLETED 但不知道 Manifest ID | 当前没有 Run -> Manifest 列表端点 | 从 Timeline 的 `run.completed` payload 取 `completion_manifest_id` |
| 控制台显示旧界面或接口不匹配 | `web/dist` 未按当前源码重建 | `cd web && npm ci && npm run build`，再重启 control-plane/重建镜像 |
| VM 本机可访问，宿主机不可访问 | 防火墙、安全组、NAT/端口转发或监听地址 | 用 `ss` 确认 0.0.0.0:8080；逐层检查 VM 网卡、UFW、宿主网络 |
| production 进程因 API Key 退出 | `SWARMOS_ENVIRONMENT=production` 且 Key 少于 32 字符 | 生成强随机值并同时更新调用方；不要降级 environment 绕过校验 |
| 数据库迁移失败 | 权限不足、旧 schema 漂移、连接串错误 | 停止发布，备份并在副本复现；不要手改 migration bookkeeping 后强启 |

## 11. 停止与清理

停止 `go run` 进程使用 `Ctrl+C`。停止本地基础设施但保留数据：

```bash
docker compose down
```

删除 volume 会永久删除本地数据库、NATS 和 Redis 数据，不属于普通停止步骤；只有明确不再需要验收数据时才执行，并先确认目标 compose project。

## 12. 发布前下一步

完成一次本地 happy path 不等于生产完成。发布前应按 [V1.5 验收矩阵](v1.5-acceptance.md) 运行自动测试、显式 PostgreSQL 合同测试和 15 项真实故障演练，并把日志、Trace、Timeline、Effect、Artifact 与 Manifest ID 归档到同一验收记录中。
