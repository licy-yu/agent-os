# SwarmOS V1.5 验收矩阵

本文把设计文档第 37 章的 15 项生产用例映射到当前代码和可执行证据。结论是：P0 主体和部分 P1 组件已经进入代码，但当前工作树没有保存 15 项真实生产拓扑演练记录，因此不能宣称 V1.5 已通过生产验收。

## 1. 证据等级

为避免把单元测试等同于生产可用，本文使用三个互不替代的等级：

- **自动验证**：仓库内可重复执行的测试或构建，验证某个实际代码路径。默认跳过的数据库测试会单独标“显式自动”。
- **合同验证**：状态机、DTO、编译器、错误分类或持久化约束证明系统会拒绝非法输入，但没有启动完整分布式拓扑。
- **待生产演练**：必须在接近生产的 PostgreSQL/Redis/NATS/Temporal/多进程/外部系统上故障注入并归档证据。当前 15 项均未发现已归档的本次工作树生产报告。

矩阵中的“部分”不是通过；只要“设计目标”尚有一段没有实现或生产证据，发布门就保持未通过。

## 3. 当前发布判断

按上述矩阵，以下 3 项存在明确实现缺口，不能通过增加人工截图来绕过：

1. Case 5：无进展后的 Self Check / Agent Switch / Replan 自动恢复；
2. Case 6：缺输入后的 WAITING_USER 与原 Checkpoint 继续；
3. Case 12：429 Backoff 或 Model Failover 自动执行。

Case 3 和 Case 14 还分别缺真实 Git 高风险 Adapter、多租户身份入口，因此也不能在当前产品边界内完整执行。其余用例已有组件基础，但仍必须做生产候选拓扑故障注入。

P2/P3 不进入 V1.5 发布验收：AgentSet、AutoScaling、A2A、Nested Swarm、Dynamic Team，以及 Evaluation Evolution/Shadow/Canary/Promotion/Rollback 均未实现。迁移文件里的前瞻表不能作为验收证据。

## 4. 自动与合同验证命令

### 4.1 默认自动测试

```bash
go test ./...
```

建议对高风险组件单独保留输出：

```bash
go test ./internal/runcontrol ./internal/planning ./internal/durabletemporal
go test ./internal/worker ./internal/contextengine ./internal/agentloop
go test ./internal/effect ./internal/toolgateway ./internal/safetycontrol
go test ./internal/execution ./internal/verification ./internal/data/postgres
go test ./internal/server ./internal/conf
```

前端构建：

```bash
cd web
npm run build
```

这些命令通过只说明当前测试覆盖的组件通过，不会自动把矩阵中的“待生产演练”改为通过。

### 4.2 显式 PostgreSQL 合同测试

真实 PostgreSQL 测试默认跳过，防止误写生产库。它们覆盖原子审批、持久 WAITING、Interaction 过期竞争、Effect 提交后 Worker 崩溃、Recovery/Prepare 并发窗口、UNKNOWN 证据收敛与授权证据保留。只能指向可丢弃的独立测试库：

```bash
export SWARMOS_INTEGRATION_DATABASE_URL='postgres://<test-user>:<test-password>@127.0.0.1:<port>/<disposable-db>?sslmode=disable'
export SWARMOS_INTEGRATION_MIGRATE=1
go test ./internal/data/postgres -run 'Postgres|HITL' -count=1 -v
```

不得把生产 DSN 填到该变量。测试完成后按测试库生命周期策略销毁整个专用数据库，而不是在共享库里手工删除未知行。

### 4.3 迁移合同

仓库包含 V1 升级 fixture 和 V1.5 assertion SQL，但当前没有把它们接成默认 Go 自动测试。上线前应在 V1 数据副本上执行：

1. 备份并验证可恢复；
2. 使用当前 control-plane 执行内嵌迁移；
3. 运行 `internal/data/migrate/testdata/v15_upgrade_assertions.sql`；
4. 核对旧 Swarm/Task/Attempt 可读、新 tenant/run/plan 字段回填、约束与索引；
5. 用发布前二进制执行只读 smoke，再允许写流量。

这属于合同/升级演练，不应直接对唯一生产库首次执行。

### 4.4 2026-08-11 上线前实测记录

目标 Ubuntu VM 的 PostgreSQL 17 隔离库已执行以下验证，连接串和密钥未进入日志或仓库：

- 全部 `Postgres|HITL` 合同测试通过，包括批准/拒绝、24 小时过期竞争、Effect commit→Suspend 崩溃窗口、Prepare/Recovery TOCTOU、UNKNOWN 成败收敛与非默认租户；
- V1 固定夹具从 000001–000003 升级到 000010，旧 Run/Task/Attempt/Artifact/Timeline 断言通过；
- 对当前业务库创建一致性 `pg_dump`，恢复到独立副本后执行 000004–000010；97 MB 数据库、约 21.6 万 Outbox 的迁移与仓储合同共耗时约 10.8 秒；
- 副本最终记录 10 个 migration、21 条已验证 tenant 复合外键，Attempt/ToolCall 租户错配均为 0；
- 该记录证明数据库迁移和持久化合同，不等同于 15 项完整分布式生产演练。

## 5. 生产演练前置环境

建议使用隔离的 Linux VM 或预生产环境，并满足：

- 与生产相同主版本的 PostgreSQL、Redis、NATS；
- TEMPORAL Case 同时运行独立 Temporal PostgreSQL、Temporal Server 和 workflow-worker；
- 至少两个普通 worker，Zombie/调度并发用例需要可独立暂停；
- 可控的 fake provider、外部 HTTP 服务和 Git remote，允许在明确边界注入错误；
- OpenTelemetry、结构化日志和 Prometheus 抓取可用；
- 测试 tenant、API Key、数据库和外部账号与生产完全隔离；
- 每个 Case 使用新的 Run 和幂等键，不复用前一 Case 的可变状态。

不要在真实客户数据、真实主仓库或真实付款/邮件/部署端点上进行 Effect 故障注入。

## 7. 15 项演练的最小判定规则

### Case 1：Worker Crash

在一个会产生多个 Checkpoint 的 Task 中记录 sequence N，终止当前 worker，等待另一 worker 接管。通过条件：新 Attempt/owner 从可恢复边界继续；已提交 Artifact hash 不变；相同 Effect key 的外部调用次数仍为 1；没有把旧 Attempt 覆盖成新 Attempt。

### Case 2：服务整体重启

在非终态 Run 中停止 control-plane、普通 worker 和 workflow-worker，再按部署顺序恢复。通过条件：数据库事实未回退；Outbox 最终发布；TEMPORAL Workflow ID 不变；Task 最终继续而非创建第二个业务 Run。

### Case 3：Git Push 后 Crash

只使用隔离 remote。让远端 ref 更新成功，在本地 Effect 完成落库前中断。通过条件：恢复时先查询 remote ref，Effect 通过 Reconcile 收敛；remote 不出现第二次提交或强推。

### Case 4：Effect UNKNOWN

外部服务接收请求后返回不确定结果。通过条件：Effect 是 UNKNOWN，直接 Execute/Retry 被拒绝；只有 Reconcile 能进入后续状态；审计保留 externalRef 与操作人。

### Case 5：连续无进展

让 Agent 连续返回不改变状态的结果。通过条件：达到守卫上限后停止当前循环，形成 Self Check 证据，再按策略切 Agent；仍失败则生成新 PlanVersion。当前自动恢复尚未实现，因此预期 verdict 为 BLOCKED，而不是手动操作后写 PASS。

### Case 6：缺少输入

Task 运行到明确缺参点。通过条件：Run/Task 进入等待状态且不占用执行槽；Input 解析为结构化 response；继续时使用原 Checkpoint，不能从头重复 Effect。当前通用编排尚未完全接线，预期 verdict 为 BLOCKED。

### Case 7：高风险 Tool

发起 R3 Effect。通过条件：审批前 Adapter 调用次数为 0；批准后恰好 1；拒绝后永久禁止授权；Interaction、Effect、Timeline 的 actor/version/idempotency 证据一致。

### Case 8：Pause

在 Task 与 Effect 活跃时 Pause。通过条件：不再绑定新 Task；正在执行的副作用先形成确定状态和 Checkpoint；PAUSED 后无后台进度；Resume 从安全点继续。仅 Run 状态立即变 PAUSED 而没有安全点证据不算通过。

### Case 9：Verification 失败

让候选结果声称成功，但外部测试命令确定失败。通过条件：required GateResult 为 FAILED/ERROR，Task 与 Run 不得 COMPLETED，失败日志以引用保存且模型文本不能覆盖它。

### Case 10：Replan

先完成 DAG 一部分并产生 Artifact，再改变目标。通过条件：出现不可变 Plan V2，V1 保留；仍有效 Artifact ID/hash 被引用而不是重建；旧未终态 Task 被取消；未决 Effect 会阻止 Replan。

### Case 11：Context 超长

产生至少 50,000 行 Tool Result。通过条件：ContextPack/模型请求不含完整原文，只含摘要、哈希和可控引用；Token 预算未被原文撑爆；敏感字段保持脱敏。

### Case 12：Provider 429

fake provider 连续返回 429。通过条件：遵守有界 Backoff 或切换允许的模型，并记入 Attempt/Cost/Timeline；不能零间隔无限重试。当前自动执行未实现，预期 verdict 为 BLOCKED。

### Case 13：Zombie Worker

暂停旧 worker 网络，使 Recovery 发放新 owner/fence，再恢复旧网络。通过条件：旧 token 的 Checkpoint/Tool/Complete 写回全部被拒绝，新 owner 可继续，Timeline 有恢复事实。

### Case 14：租户隔离

用 Tenant A/B 的独立可信身份双向请求 Run、Artifact、Interaction、Effect、Memory、Secret。通过条件：跨租户统一 404/拒绝，数据库查询无串租户，日志不泄露目标是否存在。当前固定单租户 API Key 不能完成该用例，预期 verdict 为 BLOCKED。

### Case 15：完成证据

完成一个真实 Run。通过条件：同一 Run 同时能关联 Final Artifact、VALID Completion Manifest、required GateResult、完整 Timeline 和可核对 Cost Summary；各 ID/hash/时间和因果链一致。只看到状态字符串 `COMPLETED` 不算通过。

## 8. 最终发布签字条件

只有同时满足以下条件，才可把 V1.5 标记为生产通过：

1. 默认测试、前端构建、显式 PostgreSQL 合同测试和升级副本断言全部通过；
2. Case 5、6、12、14 的实现阻断已消除；Case 3 有真实可控 Adapter；
3. 15 项在目标版本、目标拓扑全部为 PASS，没有用合同测试替代故障注入；
4. LEGACY 与 TEMPORAL 分别至少完成一次长时 Run；
5. 镜像、systemd/compose、API Key、readiness、smoke、备份恢复、TLS、告警均有证据；
6. 已知问题、例外、回滚步骤和责任人写入发布记录。

在此之前，准确表述应为：“V1.5 P0 主体与部分 P1 已实现，生产验收进行中；P2/P3 未实现。”
